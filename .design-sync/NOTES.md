## Repo shape

This repo is a Next.js app (SECP/FBR compliance tracker), not a standalone published design-system package — there is no `dist/` build, no `.d.ts` output, and no Storybook. The converter runs in **synth-entry mode**, discovering components directly from `components/*.tsx` and `components/ui/*.tsx` source.

## NavBar is deliberately excluded from the sync

`components/nav-bar.tsx` imports `next/link` and `next/navigation` (`usePathname`). Both are real, npm-resolvable modules (this app depends on `next`), so esbuild happily bundles them into the IIFE — but Next's router/link internals reference `process.env.*` far beyond the single `NODE_ENV` define the converter sets, and there's no `process` global in a static preview page. The result: the **entire** bundle threw `ReferenceError: process is not defined` at load time and `window.<Global>` never got assigned — this broke ALL 20 other, unrelated components too, not just NavBar (they share one IIFE).

Fix applied: rather than fork `lib/bundle.mjs` (forking it is explicitly disallowed by the skill — it's part of the app-contract surface) to shim `next/link`/`next/navigation`, the config uses an explicit hand-written entry (`.design-sync/entry.mjs`) that re-exports only the 20 safe components, plus `componentSrcMap` pinning each name to its real source file. This sidesteps synth-entry's blanket "bundle every non-test .tsx under `components/`" behavior, which otherwise pulls in `nav-bar.tsx` regardless of component-list exclusions.

**If NavBar (or anything else importing `next/link`/`next/navigation`/other Next-runtime-coupled modules) needs to be added later**, it cannot simply be added to `componentSrcMap` — it must either (a) get a real mock/stub via a legitimate config seam (none currently exists for whole-module shims outside `.design-sync/overrides/`, which is off-limits for `bundle.mjs`), or (b) stay excluded as app-chrome that isn't a portable design-system piece. Re-verify this doesn't regress on re-sync: `.design-sync/entry.mjs`'s export list must keep excluding `nav-bar.tsx`.

## Tailwind v4 compilation

The app's `app/globals.css` starts with `@import "tailwindcss";`, which is not a browser-loadable path — it needs Tailwind's build step to resolve into real utility CSS. `.design-sync/compile-tailwind.mjs` (durable, committed; `cfg.buildCmd`) runs `@tailwindcss/postcss` programmatically against `app/globals.css` and writes `.design-sync/.cache/tailwind-build.css` (gitignored, regenerated), which `cfg.cssEntry` points at. **Re-run `node .design-sync/compile-tailwind.mjs` whenever `app/globals.css` or any component's Tailwind class usage changes**, before rebuilding the DS bundle — otherwise new/changed utility classes silently won't be in the shipped CSS.

## Fonts: Geist / Geist Mono fetched from Google Fonts

The app loads Geist Sans/Mono via `next/font/google` (self-hosted at Next.js build time — no static font files exist in the repo). With the user's explicit OK, `.design-sync/fonts/geist.css` + the two `.woff2` files were fetched from Google Fonts' public CDN (`fonts.googleapis.com`/`fonts.gstatic.com`, OFL-licensed) — both are variable fonts, so a single file each covers the full weight range (`font-weight: 100 900`). Wired via `cfg.extraFonts`. These are durable, committed files (not regenerated by any build script) — if Geist's hosted files ever move, re-fetch via the CSS2 API: `curl -A "<modern UA>" "https://fonts.googleapis.com/css2?family=Geist:wght@400;500;600;700&family=Geist+Mono:wght@400;500&display=swap"`.

## Component grouping

Everything lands in a single `general` group. `deriveComponentsFromSrc`'s dir-based grouping treats `ui/` as a generic container name (`GENERIC_DIR`), and there's no per-component doc frontmatter to set `category`, so grouping stayed flat rather than forcing artificial subgroups.

## Re-sync risks

- **`.design-sync/entry.mjs` is hand-maintained.** If a new component is added under `components/` or `components/ui/`, it must be added to `entry.mjs`'s exports AND to `cfg.componentSrcMap` — the synth-entry auto-discovery is bypassed by design (see NavBar note above), so new components will NOT appear automatically on a re-sync.
- **`cfg.dtsPropsFor` is hand-written** for all 20 components (no real `.d.ts` exists to extract from). If a component's actual prop signature changes in source, the shipped `.d.ts` will silently drift from reality until someone updates `dtsPropsFor` to match.
- **The compiled Tailwind CSS is a build artifact**, not hand-maintained — but it's only as fresh as the last `compile-tailwind.mjs` run. A re-sync that forgets to re-run it (or skips `cfg.buildCmd`) ships stale styles.
- **Font files were fetched once, manually** — not re-verified against the app's actual `next/font` output on each sync. If the app changes font families/weights in `app/layout.tsx`, `.design-sync/fonts/geist.css` needs a matching manual update.
